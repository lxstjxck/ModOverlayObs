# ModOverlayObs

Веб-панель для управления оверлеем в OBS. Каждый Twitch-стример может подключить собственный канал с независимым полотном, медиа и OBS URL. Модераторы размещают текст, изображения, GIF, видео и аудио; OBS показывает результат через источник «Браузер». Начальный размер полотна — 1920 × 1080.

## Возможности

- Загрузка файлов и добавление медиа по прямой ссылке, ссылке YouTube или eblo.id.
- Перемещение, изменение размера, обрезка, поворот и настройка прозрачности элементов.
- Управление воспроизведением, временем начала, громкостью и зацикливанием медиа.
- Смайлы канала Twitch, активного набора 7TV и собственные ссылки на изображения.
- Синхронизация панели и оверлея через Socket.IO; хранение настроек в SQLite.
- Twitch TTS для каждого подключённого канала: команда `!tts` для владельца и модераторов, награда за баллы канала для остальных зрителей.

## Локальный запуск

Нужен Node.js 22.12+ и npm. Скопируйте `.env.example` в `.env` и задайте `SESSION_SECRET` длиной от 32 символов. Для нового Twitch-only сервера настройте Twitch OAuth и оставьте `INITIAL_ADMIN_PASSWORD` пустым: legacy OWNER и пустой legacy-канал не создаются. Если нужен старый парольный вход, задайте собственный `INITIAL_ADMIN_PASSWORD` длиной не менее 12 символов. Только для **новой пустой базы** выполните:

```bash
npm ci
npm run db:prepare
npx prisma migrate deploy
npm run dev
```

Страница входа откроется по адресу `http://localhost:5173/login`. Существующая панель доступна через вход по паролю на `/legacy-login`. `INITIAL_ADMIN_USERNAME` и `INITIAL_ADMIN_PASSWORD` из `.env` применяются только при создании первого аккаунта; их изменение не меняет пароль существующего владельца.

Если пароль legacy-владельца утрачен, остановите приложение, задайте временную переменную `OWNER_RESET_PASSWORD` в локальном `.env` (уникальный пароль длиной от 12 символов) и проверьте целевую базу. Затем запустите сброс с `--apply`:

```powershell
$dbPath = (Resolve-Path -LiteralPath database/modoverlay.db).Path
node scripts/reset-legacy-owner-password.mjs --database $dbPath
node scripts/reset-legacy-owner-password.mjs --database $dbPath --apply
```

Скрипт требует ровно одну legacy OWNER-запись, перед изменением создаёт проверенную резервную копию в `backups/`, меняет только её хеш пароля и удаляет её активные сессии. После проверки входа удалите `OWNER_RESET_PASSWORD` из `.env` и перезапустите приложение. Не передавайте пароль в командной строке или чате.

### Twitch OAuth и подключение каналов

Создайте **Confidential** приложение в Twitch Developer Console. Укажите `TWITCH_CLIENT_ID`, `TWITCH_CLIENT_SECRET`, `TWITCH_OAUTH_REDIRECT_URI` и постоянный `OAUTH_TOKEN_ENCRYPTION_KEY` в локальном `.env`. Ключ — 32 случайных байта в виде 64 шестнадцатеричных символов; команда генерации есть в `.env.example`. Не меняйте ключ после входа пользователей без отдельной процедуры переноса токенов.

Для Vite proxy зарегистрируйте точные Redirect URL `http://localhost:5173/api/auth/twitch/callback` и `http://localhost:5173/api/tts/callback`; для прямого доступа к серверу используйте порт 4000. В production нужны оба точных URL на публичном HTTPS-адресе; `PUBLIC_ORIGIN` и `ORIGIN_ALLOWLIST` должны соответствовать ему. TTS использует отдельное согласие владельца через существующий callback `/api/tts/callback`.

Откройте `/login` и войдите через Twitch один раз. Вход запрашивает `moderation:read` и `user:read:moderated_channels`. В `/channels` доступны собственный канал и каналы, где аккаунт назначен модератором; переключатель канала не требует повторного входа. Роль определяется сервером отдельно для каждого канала. В панели собственного канала нажмите «Подключить канал»: сервер повторно проверит Twitch ID и создаст канал с собственным секретным OBS URL. Повторное нажатие вернёт тот же канал. OBS, настройки канала, список модераторов и TTS доступны только владельцу соответствующего канала. Для привязки старого канала используйте `/api/auth/twitch/start/bind` из legacy OWNER-сессии: после привязки откроется единая Twitch-сессия, а парольный Legacy-вход останется доступным. TTS подключается отдельно в панели своего канала; старый канал продолжает работать через legacy OBS Setup.

При обновлении старые Twitch-сессии потребуют нового входа, чтобы подтвердить оба разрешения. Старые записи OAuth, подключённые каналы, OBS URL, медиа, настройки и Legacy-вход сохраняются. Схема SQLite не меняется: новая запись OAuth с режимом `unified` создаётся в существующей таблице после входа. Если Twitch отказывает в разрешении, токен отозван или API проверки недоступен, доступ к каналу закрывается до успешной повторной проверки.

Безопасное развёртывание этого изменения: остановите приложение, сохраните согласованную копию SQLite (включая WAL, если он есть) и `uploads/`, установите зависимости и соберите новую версию, затем запустите приложение с прежними секретами окружения. Новая миграция и `db:push` не нужны. Войдите через Twitch заново и проверьте собственный канал, модерируемый канал, существующий OBS URL, Legacy-вход и TTS. Если потребуется откат к старой версии кода, данные остаются совместимыми; Twitch-вход в старой версии потребуется повторить.

### Обновление существующей SQLite-базы

`prisma migrate deploy` выдаёт P3005 на непустой базе без истории Prisma. Baseline `20261011_initial_baseline` описывает исходную схему до OAuth; на существующей базе её нужно зарегистрировать через `migrate resolve --applied` только после проверки исходных таблиц, столбцов и индексов. Изменения OAuth могли уже попасть в схему через прежний `prisma db push`; перед регистрацией stage1 проверьте её отдельным скриптом.

Остановите приложение и сохраните копию `uploads/`. В PowerShell из корня проекта выполните:

```powershell
$dbPath = (Resolve-Path -LiteralPath database/modoverlay.db).Path
node scripts/backup-sqlite.mjs $dbPath
node scripts/inspect-sqlite-migrations.mjs $dbPath
node scripts/reconcile-twitch-oauth-stage1.mjs --database $dbPath
```

Копия создаётся согласованно через SQLite `VACUUM INTO` в исключённом из Git каталоге `backups/`; скрипт проверяет целостность исходной базы и копии. `inspect-sqlite-migrations.mjs` показывает таблицы, индексы, числа записей, состояние журнала Prisma и SHA-256 отпечатки существующих пользователей, канала (включая секретный OBS-токен без его вывода), медиа и настроек. Сохраните этот вывод для сравнения после обновления. Перед записью в рабочую базу отрепетируйте команды ниже на **отдельной копии** резервной базы, указав её абсолютный путь.

Если проверка первой миграции показывает отсутствующие объекты, восстановите только их:

```powershell
node scripts/reconcile-twitch-oauth-stage1.mjs --database $dbPath --apply
node scripts/reconcile-twitch-oauth-stage1.mjs --database $dbPath
```

Скрипт сверяет SQL первой миграции с таблицами, столбцами и индексами, выполняет только недостающие аддитивные операции в одной транзакции и проверяет результат. При несовместимой уже существующей схеме он останавливается без регистрации миграции; требуется ручной разбор. Если вывод `missing` пуст, `--apply` не нужен. Старый `scripts/apply-twitch-oauth-migration.mjs` использует отдельный журнал `SchemaMigration` и не заменяет регистрацию в Prisma.

SQL опубликованных миграций не изменён. Для правильной сортировки `20261012_channel_access_stage2` и `20261012_channel_identity_unique` переименованы в `20261013_channel_access_stage2` и `20261013_channel_identity_unique`. Старые имена могут уже находиться в журнале Prisma: после проверки объектов соответствующего этапа зарегистрируйте новое имя через `migrate resolve --applied`, чтобы SQL не выполнился повторно. Если этап ещё не применялся, не регистрируйте его: `migrate deploy` выполнит его. Отчёт `inspect-sqlite-migrations.mjs` показывает журнал, таблицы, столбцы и индексы. При частично применённом этапе остановитесь.

На копии базы, а затем при утверждённом обновлении на остановленной рабочей базе, выполните только подходящие команды:

```powershell
$env:DATABASE_URL = 'file:' + $dbPath.Replace('\','/')
# Только если исходная схема есть, а baseline ещё не записана.
npx prisma migrate resolve --applied 20261011_initial_baseline
# Только если stage1 полностью присутствует и ещё не записана.
npx prisma migrate resolve --applied 20261012_twitch_oauth_stage1
# Только если старый stage2 записан и его объекты полностью присутствуют.
npx prisma migrate resolve --applied 20261013_channel_access_stage2
# Только если старый identity_unique записан и уникальный индекс присутствует.
npx prisma migrate resolve --applied 20261013_channel_identity_unique
npx prisma migrate deploy
npx prisma migrate status
npx prisma migrate diff --from-url $env:DATABASE_URL --to-schema-datamodel prisma/schema.prisma --script
npx prisma generate
node scripts/inspect-sqlite-migrations.mjs $dbPath
```

Если миграция уже числится под новым именем, пропустите соответствующий `migrate resolve`. Старые записи остаются в истории; Prisma 6.12 после регистрации новых имён сообщает `Database schema is up to date!`. Перед `20261013_channel_identity_unique` проверьте отсутствие дубликатов непустого `twitchBroadcasterId` в копии базы. `migrate diff` должен вывести `This is an empty migration`. После обновления сравните отпечатки и числа записей, проверьте legacy-вход, Twitch OAuth и прежний OBS Overlay URL. Не применяйте к существующей базе `migrate reset`, `db push --force-reset` или `--accept-data-loss`. Контейнер не меняет схему при старте; обновление production требует отдельной подготовки и резервной копии.

Полотно делится на область **SPAWN** для подготовки элементов и область внутри красной рамки, которую видит OBS. Изменения элементов внутри рамки отображаются в оверлее сразу.

## Подключение OBS

1. Откройте **OBS Setup** в панели и скопируйте **Overlay URL**.
2. Добавьте в OBS источник «Браузер» с этим URL и размером **1920 × 1080**.
3. Разместите источник выше тех источников сцены, которые оверлей должен перекрывать.

Overlay URL содержит токен доступа. Не публикуйте его. Если ссылка раскрыта, обновите токен в **OBS Setup** и замените URL в OBS.

## Запуск собранной версии

Укажите в `.env` `NODE_ENV=production` и публичный HTTPS-адрес в `PUBLIC_ORIGIN`. Для уже существующей базы сначала выполните процедуру обновления выше. Только при первом запуске на новой пустой базе установите зависимости и создайте схему:

```bash
npm ci
npm run db:prepare
npx prisma migrate deploy
npm run build
npm start
```

Приложение слушает порт из `PORT` (по умолчанию 4000). HTTPS можно настроить перед ним через обратный прокси. Также доступен `docker compose up -d --build`; стандартный контейнер не включает Python и модель для TTS.

## Twitch и TTS

Каждый владелец подключает TTS для своего канала отдельно в `/streamer`. Обычный Twitch-вход не получает TTS scopes; отдельное согласие запрашивает только `user:read:chat` и `channel:manage:redemptions`. Legacy-владелец использует прежнюю страницу OBS Setup.

Для смайлов Twitch и TTS нужны `TWITCH_CLIENT_ID` и `TWITCH_CLIENT_SECRET` от приложения в [Twitch Developer Console](https://dev.twitch.tv/console/apps). Смайлы 7TV доступны и без этих ключей, если указать Twitch ID канала в панели.

Для TTS дополнительно установите PyTorch и Silero в отдельное Python-окружение и задайте полный путь к его интерпретатору в `TTS_PYTHON`. В настройках приложения Twitch укажите OAuth Redirect URL в точном виде `<PUBLIC_ORIGIN>/api/tts/callback`. После запуска каждый стример подключает TTS в `/streamer`, включает его и при необходимости создаёт награду. Начальная стоимость — 1000 баллов; её можно менять в панели. Для legacy-канала используйте OBS Setup.

Владелец, ведущий и обычный модераторы отправляют `!tts текст` в чат без награды. Остальные зрители, включая VIP, вводят текст при использовании награды. Ограничение — 200 символов и одна фраза на пользователя каждые 30 секунд. Озвучка использует Silero `v3_1_ru`, голос `baya`.

Для вывода звука в OBS включите у источника «Браузер» **Control Audio via OBS**. Чтобы звук был слышен и в эфире, и через мониторинг OBS, выберите **Monitor and Output** в расширенных настройках аудио.

Диагностические сообщения TTS можно временно включить через `TTS_DEBUG=1` в `.env`. Они не содержат текст сообщений, имена пользователей или токены. Синтезированные WAV хранятся в `uploads/.tmp/` только во время обработки и удаляются после воспроизведения или ошибки.

Сервер открывает одно EventSub WebSocket-подключение на разрешённый TTS-канал и восстанавливает включённые подключения после перезапуска. Очереди и статусы разделены по каналам (до 10 ожидающих фраз на канал и 100 суммарно); Python-генерация общая, одновременно обрабатывается одна фраза, а воспроизведение в OBS каждого канала идёт независимо. Отключение или отзыв авторизации одного канала не останавливает остальные. Отзыв требует повторного подключения в панели. Новых миграций БД для TTS нет: используются существующие зашифрованные настройки и таблица одноразовых OAuth-состояний.

Ручная проверка двух каналов: войдите двумя разными Twitch-стримерами, подключите каналы и TTS, откройте отдельные OBS Browser Source с их URL. Отправьте `!tts` в оба чата одновременно и проверьте, что каждая фраза звучит только в своём OBS. Создайте награду для каждого, проверьте стоимость и возврат баллов при отключённом OBS. Выключите TTS первого канала и повторите команду во втором; затем перезапустите локальный сервер и проверьте восстановление только включённых каналов. Для фактического звука в OBS нужен ручной тест с `Control Audio via OBS` и `Monitor and Output`.

## Данные и проверки

SQLite-база хранится в `database/`, загруженные файлы — в `uploads/`. Сохраняйте резервные копии обеих папок. `.env`, базу, загруженные файлы и Overlay URL не добавляйте в репозиторий. Дополнительные сведения — в [обзоре безопасности](docs/security-review.md).

```bash
npm run typecheck
npm run lint
npm test
npm run build
```
