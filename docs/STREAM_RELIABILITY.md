# Надёжность трансляции и восстановление — 16 октября 2026

## Телеметрия HTML5-медиа после reconnect

OBS Browser Source отправляет `media:status` для каждого видео и аудио HTML5 примерно раз в секунду и сразу после смены playback-состояния. Сообщение содержит ID элемента, ID текущего OBS-сокета, позицию, длительность, признак воспроизведения и ID последней применённой команды. Сервер проверяет форму данных, ID сокета и принадлежность элемента каналу по авторизованному соединению. Статусы находятся только в памяти, раздельно для каждого OBS, ограничены по частоте и удаляются при отключении сокета. Таймкоды не записываются в SQLite.

После восстановления Socket.IO OBS сообщает фактическую позицию существующего плеера. Повторный `overlay:state` с тем же ID команды не вызывает повторный Restart, Seek или Play; локальный Loop продолжает работать во время краткой недоступности сервера. Редактор показывает выбранный источник OBS и его фактическое время. Если статус пропал более чем на 5 секунд или OBS отключился, показывается OFFLINE. Для YouTube доступно только время локального предпросмотра с явной подписью; оно не считается телеметрией OBS.

Автоматические проверки покрывают два OBS с разными позициями, reconnect, Pause/Seek, очистку при отключении, межканальную изоляцию и отзыв токена. Ручной тест настоящего OBS остаётся обязательным пунктом приёмки; шаги описаны в [staging-проверке](STAGING_PLAYBACK.md).

## Как проводились проверки

Все автоматические проверки выполняются локально. `tests/securityIntegration.test.ts` создаёт отдельный временный каталог, SQLite-базу и `uploads`, подменяет ответы Twitch и удаляет фикстуры после завершения. Production SQLite, пользовательские файлы и секреты не используются. OBS Browser Source, реальная сеть и кодеки в этом прогоне не запускались.

Сервер проверяет OBS-токен при каждом Socket.IO подключении и выдаче `/uploads`. Редакторы получают доступ через Twitch-сессию и роль на конкретном канале. Сцена для OBS восстанавливается из SQLite при каждом подключении; промежуточные `preview:transform` не сохраняются. Полная сцена `overlay:state` отправляется при подключении и после канонических изменений. Временные файлы загрузки очищаются при старте и затем раз в час, не более 100 за проход; TTS-файлы имеют отдельную очистку.

## Предлагаемые SLO для staging

- После восстановления сети или перезапуска сервера 95% OBS Browser Source должны получить канонический snapshot не позже 10 секунд. Измерять от доступности сервера до получения `overlay:state` в браузере.
- При подтверждённом отзыве OBS-токена сцена должна очиститься не позже 1 секунды после события `access:revoked` или отказа авторизации. Проводить с активным и спящим источником OBS.
- За час нагрузки с пятью каналами: 0 пересечений комнат, 0 повреждённых транзакций SQLite, 0 необработанных отказов `play()`, 0 удалений активных временных файлов.
- После возврата OBS число элементов должно равняться числу элементов канонического snapshot; повторное получение snapshot не должно повторять одноразовые команды воспроизведения в той же странице.

Локальный тест записывает только число каналов и сокетов, счётчики ошибок, задержки, CPU, RSS, heap, свободное место и число временных файлов. Он не выводит содержимое сцены, cookie, OAuth, OBS URL или токены. Для staging замеры следует собирать отдельно по интервалам и проверять p95, а не переносить цифры одного локального запуска.

## Ручная проверка в OBS на отдельном staging

1. Подготовить отдельную SQLite-базу и каталог uploads. Загрузить MP4 10, 50 и до 100 МиБ с известными H.264/AAC профилями и отдельный повреждённый файл. Зафиксировать кодеки и контрольные суммы.
2. Для двух каналов открыть по OBS Browser Source, затем повторить с тремя и пятью. Проверить слои, геометрию 1920×1080, mute, volume, loop, seek в начало/середину/конец, play/pause/stop/restart.
3. Прервать сеть на несколько секунд: убедиться, что последний кадр сцены не исчезает. Вернуть сеть и проверить канонический snapshot. Затем отозвать токен и убедиться, что сцена очищается сразу.
4. Закрыть один OBS при втором активном, отключить и вернуть источник, перезапустить OBS и staging Node.js. Проверить ONLINE/OFFLINE, число соединений, отсутствие дублей и поведение уже запущенного видео.
5. Повторить с отсутствующим, повреждённым и неподдерживаемым видео. Убедиться, что отказ не вызывает бесконечную перезагрузку и что ресурсы освобождаются после закрытия источника.

## Оставшиеся риски

Проверка свободного места выполняется перед крупной загрузкой и резервирует ожидаемый объём внутри одного процесса. Если SQLite, uploads или логи расположены на разных томах, администратор должен следить за каждым томом отдельно. Внешние процессы могут занять диск после проверки. Для маленьких запросов до 10 МиБ ранняя проверка не выполняется.

Тесты Range используют синтетические файлы нужного размера. Они подтверждают HTTP-доступ и потоковую выдачу, но не декодирование, timing, stall/abort или поведение Chromium внутри OBS. Ошибка `play()` теперь безопасно обрабатывается; автоматический повтор не добавлен, чтобы повреждённый файл не создавал цикл.
