# План: Twitch OAuth, несколько каналов и разрешение холста

Статус: анализ для будущей реализации; исходный код, схема и production-настройки на этом шаге не изменялись. Основание — ТЗ пользователя, текущий репозиторий и `AGENTS.md` (12 октября 2026). Действия с рабочей SQLite-базой или VPS не выполнялись.

## Совместимость и ключевые решения

Реализация возможна без переписывания редактора. `Streamer` уже содержит `canvasWidth`, `canvasHeight`, `overlayToken`, Twitch ID и связи с `Media`, `PreviewElement`, `LiveInstance`, `CustomEmote`, `AuditLog`. Его лучше сохранить как внутреннюю сущность канала и сохранить существующие `id`/внешние ключи; в API/UI назвать каналом. Новой таблицы `ChannelSettings` для двух полей холста пока не нужно: это аддитивное расширение `Streamer`. Позже отдельная таблица оправдана только при настройках с отдельным жизненным циклом.

Главные блокеры — глобальные роли/права `User`, повсеместный `getDefaultStreamer()`, отсутствие выбора канала в HTTP/Socket.IO, глобальное состояние Twitch TTS и фиксированный размер OBS-клиента. Выбор интерфейса «Стример/Модератор» не участвует в авторизации. Сервер определяет владельца по Twitch ID и связи с каналом, модератора — по свежему подтверждению Twitch и локальному запрету. Существующая роль `OWNER` остаётся только для legacy-входа и восстановления; она не выдаёт автоматически права на произвольный канал.

В текущей версии `PreviewElement` фактически является полотном OBS: `socket.ts` посылает `getPreviewState` в `overlay:state`, а `preview:transform` немедленно ретранслируется в `overlay:transform`; `LiveInstance` — отдельный поток команд/метаданных. Поэтому термин «предпросмотр изменения разрешения» означает временный, только локальный расчёт будущей композиции. Он не должен создавать `PreviewElement`, менять SQLite или слать сокет-события. Сохраняются SPAWN за рамкой, существующие live/preview потоки и каноническая загрузка при reconnect.

## Предлагаемая модель и границы доступа

- Сохранить `Streamer` и его ID как `channelId`; добавить уникальный `twitchBroadcasterId`, `ownerUserId` (nullable до привязки), `avatarUrl`, `moderatorsSyncedAt`, `canvasRevision`/эквивалент. `canvasWidth/Height`, `settingsJson`, `overlayToken` остаются. Не переименовывать существующие поля и связи без нужды.
- В `User` добавить уникальный nullable `twitchUserId`, отдельные Twitch login/avatar/displayName; сохранить legacy `username`, `passwordHash`, `role`, `permissionsJson` для восстановления. Twitch-пользователь не получает глобальный `OWNER`; нужно различать источник входа/набор полномочий. Для пользователей без пароля nullable hash либо закрытый неприменимый hash с явной проверкой типа аккаунта.
- `TwitchOAuthConnection`: уникальный `(twitchUserId, purpose)` или `(userId, purpose)` для `LOGIN_MODERATOR` / `CHANNEL_OWNER_TTS`, зашифрованные access/refresh, scopes, expiry, checkedAt, revokedAt; владелец может получить дополнительные scopes при включении TTS. Учесть одновременный refresh per connection и атомарное сохранение нового refresh token. Лучше отдельный стабильный ключ шифрования, не `SESSION_SECRET`; старые TTS данные расшифровать старым ключом при переходе и перешифровать, без логирования.
- `ChannelModeratorAccess`: `(streamerId, twitchUserId)` unique, `allowed`/`denied`, `updatedAt`, `updatedBy`; запрет имеет приоритет над свежим Twitch-статусом и не стирается синхронизацией. Отдельно хранить снимок действующих модераторов/время полной успешной синхронизации либо проверять конкретный ID через `Get Moderators` и вести кэш с ограниченным TTL. Отсутствие в полном успешном снимке отзывает доступ; частичный ответ, 429/5xx и сбой пагинации не обнуляют список и не дают бессрочное разрешение.
- Для `Media`, `PreviewElement`, `LiveInstance` проверять не только `streamerId`, но и принадлежность связанных `mediaId`/`previewElementId` тому же каналу; сырые `src` и `propsJson` не должны обходить чтение защищённых файлов. Overlay URL — bearer-секрет только для чтения состояния/медиа/проигрывания TTS, без мутаций. Владелец видит и перевыпускает только свой URL. Не включать токены в обычные channel DTO, API-списки, логи, внешние медиа URL.
- Доступ модератора: действующая сессия Twitch пользователя **и** свежий Twitch-статус модератора данного канала **и** отсутствие локального запрета **и** соответствующий permission flag. Режим в UI этого не меняет. Административный legacy-аккаунт имеет доступ лишь к явно разрешённому старому каналу до/после привязки; другие каналы не видит. Владельцу не нужен модераторский статус для своего канала.

## Безопасная миграция существующей базы

1. До развёртывания: остановить единственный процесс приложения, зафиксировать текущий commit и секреты окружения в защищённом хранилище, убедиться в наличии свободного места. Сделать согласованную SQLite-копию через SQLite backup API/`VACUUM INTO` либо при полностью остановленном процессе скопировать DB вместе с WAL/SHM; сохранить `uploads/` и `.env` отдельно, проверить открытие копии и выборочные размеры/счётчики/файлы. `SESSION_SECRET` нужен для старого TTS. Не хранить резервные копии в Git.
2. Проверить миграцию на **копии** production-базы в изолированном каталоге: зафиксировать counts и ID таблиц `Streamer`, `Media`, `PreviewElement`, `LiveInstance`, `CustomEmote`, `AuditLog`, `Settings`, отсутствие сирот и путь БД через `PRAGMA database_list`. Тестовый запуск не должен видеть `database/modoverlay.db`.
3. Аддитивная схема: новые nullable поля/таблицы/индексы, без удаления/переименования старых `streamerId` и без смены `overlayToken`/путей файлов. Скрипт миграции с журналом версий и идемпотентным upsert; при повторном запуске те же записи и counts. Для уникальности Twitch ID сначала обнаружить дубликаты/несоответствия, затем создать constraint. Существующий канал остаётся неприкреплённым до явной проверки владельца.
4. Привязка: владелец входит под legacy OWNER и проходит Twitch OAuth в той же защищённой сессии; сервер проверяет постоянный Twitch User ID, согласованность с уже сохранёнными `twitchBroadcasterId` и TTS broadcaster ID. Если IDs не совпали — остановить привязку и дать ручную процедуру разрешения конфликта, не менять идентичность по похожему логину. В одной транзакции назначить owner и уникальный broadcaster ID, сохранить аудит; старые медиа, URL, размеры и reward ID остаются. После проверки входа через Twitch оставить legacy recovery доступным только к этому каналу.
5. Переводить API/клиент на явный channel context до разрешения регистрации второго канала. При ошибке откатить приложение и БД на согласованную копию **вместе** с uploads/секретами, либо применить проверенный forward fix; после появления новых записей простой откат только бинарника или только схемы небезопасен. Проводить миграцию VPS лишь по отдельной команде пользователя.

Не применять `db:push` к рабочей БД как универсальную миграцию: текущий Dockerfile запускает его на каждом старте. Для production нужен отдельный версионированный, проверенный на копии шаг с остановкой сервиса и явным контролем результата. Никаких destructive reset/ручного редактирования SQLite.

## Twitch OAuth, scopes и окружение

Зарегистрировать **Confidential** Twitch application. Callback для нового входа: точный HTTPS URL `<PUBLIC_ORIGIN>/api/auth/twitch/callback` (планируемый маршрут); существующий TTS callback `<PUBLIC_ORIGIN>/api/tts/callback` нужен до перевода TTS на новое подключение. Для локальной разработки отдельно зарегистрировать точный `http://localhost:5173/api/auth/twitch/callback` при Vite proxy либо `http://localhost:4000/api/auth/twitch/callback` при прямом backend, выбрав реально используемый origin. `redirect_uri` при обмене кода должен совпасть с начальным и зарегистрированным URL. Пользовательский публичный адрес может отличаться от локального `DOMAIN`; сначала определить одну каноническую внешнюю HTTPS точку.

| Режим/функция | Минимальные scopes | Назначение |
| --- | --- | --- |
| Вход и профиль | Нет дополнительных scopes | Authorization Code Flow даёт user token; `Get Users` возвращает ID, login, имя и аватар без `user:read:email`. |
| Модератор | `user:read:moderated_channels` | `Get Moderated Channels` для **своего** Twitch User ID. |
| Стример | `moderation:read` | `Get Moderators` только для канала, чей broadcaster ID совпадает с владельцем user token. |
| TTS, по отдельному согласию владельца | `user:read:chat`, `channel:manage:redemptions` | Существующие `channel.chat.message`, награда и изменение статуса redemption. Не запрашивать TTS scopes модератору. |
| Смайлы | Нет user scopes | Существующий app token (`client_credentials`) для публичных Twitch emotes; 7TV отдельно. |

Проверить реальный набор scopes в ответе/`/validate`; недостающие запрашивать повторным согласием, не считать режим интерфейса полномочием. OAuth `state` — случайный одноразовый, привязан к браузеру/сессии, режиму, redirect и короткому TTL, с атомарным consume и защитой replay/login CSRF; callback обрабатывает отказ, меняет код только сервером, после успеха делает редирект на URL без `code`/`state`. Новая сессия — HttpOnly, Secure в production, SameSite=Lax; текущий CSRF и проверка Origin остаются для мутаций. Токены хранятся только на сервере, шифруются отдельным стабильным секретом, не попадают в cookie/JSON/логи; `GET /validate` при запуске и затем по требованиям Twitch, при 401 — контролируемый refresh/повторное согласие, при disconnect — revoke и отзыв доступа. Обычный logout завершает сессию; отключение Twitch интеграции — отдельная операция с отзывом token и зависимых сессий.

Изменения `.env.example` **на этапе реализации**: оставить `TWITCH_CLIENT_ID`, `TWITCH_CLIENT_SECRET`; добавить, например, `TWITCH_OAUTH_REDIRECT_URI` с точным публичным callback (либо документированное вычисление из `PUBLIC_ORIGIN`), `OAUTH_TOKEN_ENCRYPTION_KEY` (стабильный случайный 32-байтный ключ, format фиксировать), параметр TTL проверки ролей при необходимости. `PUBLIC_ORIGIN`, `ORIGIN_ALLOWLIST` и `SESSION_SECRET` должны описывать канонический HTTPS origin и безопасные cookie/старый TTS. Никаких `VITE_` переменных с Twitch secret. При переносе старого TTS не менять `SESSION_SECRET` до перешифрования. Настройки приложения и redirect URL задокументировать для VPS/локальной разработки.

Основание по Twitch: [Authorization Code Flow](https://dev.twitch.tv/docs/authentication/getting-tokens-oauth/), [Get Moderators и Get Moderated Channels](https://dev.twitch.tv/docs/api/reference/), [scopes](https://dev.twitch.tv/docs/authentication/scopes/), [валидация токенов](https://dev.twitch.tv/docs/authentication/validate-tokens/), [refresh](https://dev.twitch.tv/docs/authentication/refresh-tokens/), [EventSub WebSocket](https://dev.twitch.tv/docs/eventsub/handling-websocket-events/).

## Разрешение холста и изменение геометрии

- Текущие 1920×1080 становятся значением по умолчанию для старого/нового канала, а не общей константой. Данные редактора хранятся в логических пикселях **Base Canvas Resolution**; Output Resolution OBS не используется. Сервер выдаёт размер вместе с начальным состоянием overlay, затем обновляет его при сохранении. OBS Browser Source пользователь вручную ставит в тот же Width/Height.
- Предустановки ТЗ: 1920×1080, 2560×1440, 3840×2160, 1280×720, 1080×1920, 720×1280, custom. Предложение для custom до реализации: целые 320–7680 на ось, положительные, `width/height` от 1/4 до 4; согласовать с границами `validation.ts` и реальной нагрузкой OBS. Сервер — источник проверки. UI показывает отношение, рамку и два сценария изменения.
- Вариант A: меняется только `canvasWidth/Height`; x/y/width/height, `props.crop*`, rotation и остальные свойства preview/live остаются в пикселях. Элементы могут оказаться за рамкой; это ожидаемо для SPAWN и показывается до сохранения.
- Вариант B: `x,width,cropLeft,cropRight` умножить на `scaleX`, `y,height,cropTop,cropBottom` — на `scaleY` для **обоих** `PreviewElement` и `LiveInstance`; сохранять координаты вне рамки и порядок слоёв. Поворот — угол в градусах, не умножать. Для объектов с зафиксированным aspect ratio вычислять новый центр по двум осям и единый размерный множитель `min(scaleX, scaleY)` либо явно предупреждать о нарушении пропорций; правило зафиксировать тестом до запуска. Масштабировать только известные размерные свойства `props` (например, размер шрифта/толщина обводки) с явной политикой для неравномерного перехода; цвет, громкость, время, источники и ID не трогать. Crop ограничить после масштабирования так, чтобы видимая область оставалась положительной.
- Предпросмотр — вычисление на копии объектов. Сохранение — одна SQLite-транзакция с ожидаемой старой размерностью/`canvasRevision`, обновлением геометрии и записью аудита; не допускать старых transient/`preview:update` во время смены ревизии. После commit разослать новый размер и каноническое состояние в комнаты канала, сбросить временные transform/undo; reconnect загружает каноническую версию. При ошибке не менять размер и элементы. Не делать автоматический push из локального предпросмотра.
- Проверить overlay размер, прозрачность и разные соотношения сторон в реальном OBS; CSS масштабирует логическое полотно, но сам Browser Source не меняет размер от обновления сайта. Особо проверить `OverlayPage.tsx` (сейчас 1920×1080), `CanvasStage`, crop/Alt Crop, zoom колесом, snapping, видео и YouTube.

## Этапы и отдельные коммиты

Каждый пункт — отдельный логический коммит после focused tests и стандартных проверок; этап с незавершённым серверным контролем доступа не открывает регистрацию второго канала.

1. `docs: migration and deployment runbook` — проверяемый backup/restore, карта старой БД, feature gate второго канала, staging-процедура; тест изоляции временной БД. Убрать автоматическую production-миграцию из запуска только вместе с рабочей заменой.
2. `db: additive channel identity and oauth models` — поля/таблицы/индексы и повторно запускаемый backfill; проверка counts/ID и неизменности старого overlay URL/reward на копии.
3. `auth: Twitch code flow and legacy recovery` — Twitch ID, state/callback/session, режимы входа, token store/refresh/revoke; вход владельца/модератора, повторный вход, явная безопасная привязка старого канала. Legacy-права ограничить старым каналом.
4. `auth: per-channel access and moderator sync` — `Get Moderators`/`Get Moderated Channels`, pagination, TTL/успешные снимки, сохранение запретов, проверки на каждом HTTP/Socket.IO действии, мгновенный revoke активных сокетов. Обновить security review.
5. `server: channel-scoped media, emotes and realtime` — убрать default streamer из рабочих API, защитить `/uploads`, сохранить HEAD/Range/quota/cleanup и preview/live пайплайн; изоляционные тесты с двумя каналами. Только после этого включить создание следующего канала.
6. `server: channel-scoped Twitch TTS` — перенести старое TTS подключение/награду, EventSub и очереди на конкретный канал, лимиты воркеров и тесты статусов/отключения OBS.
7. `client: streamer dashboard and moderator channel picker` — обзор/OBS Setup/модераторы/настройки, список каналов, причины запрета, маршруты редактора, переключение контекста; убрать подставленный `owner` из новой формы, сохранить отдельный recovery-вход.
8. `canvas: per-channel base resolution` — shared/API/socket размер и ревизия, OBS renderer, валидаторы/presets, read-only предпросмотр, атомарные варианты A/B, обновление инструкций OBS; геометрические и браузерные тесты.
9. `docs: production rollout and compatibility` — README, `.env.example`, Docker/deploy инструкции, матрица ручной проверки OBS/TTS и финальный аудит секретов/диффа.

При необходимости этапы 4–5 объединяются в одном релизе: между ними нельзя допустить второй канал при неполной изоляции. Новые контракты API/Socket.IO вводить совместно с клиентом; поддержка старого URL/токена остаётся для существующего OBS до явной ротации.

## Production VPS: риски и выпуск

- **Данные:** SQLite schema change, автоматический `db push` из Dockerfile, возможные WAL-файлы и инцидент с перезаписью рабочей базы, уже описанный в `docs/security-review.md`. Нужны остановка сервиса, проверенная offline-копия БД/uploads, репетиция миграции и пути БД, контрольный запуск одного экземпляра. Не выполнять миграцию на VPS без отдельного подтверждения.
- **Доступ:** старые глобальные `OWNER`/permissions, `/uploads` по cookie, `/streamer` с `overlayToken`, `/obs` и ручная смена Twitch login сейчас рассчитаны на один канал; до включения регистрации нового канала все эти входы должны быть изолированы. Ротация токена разрывает OBS и в текущем коде очищает live instances — показать подтверждение и сохранить поведение осознанно. Overlay URL как секрет может попасть в журналы обратного прокси; редактировать access log для `/overlay/…` и query токена в `/uploads`, не включать их в аналитику/скриншоты.
- **Twitch:** 401/revoke, 429 и неполная пагинация не должны давать бесконечный доступ; рекомендованный начальный TTL положительной проверки 5 минут, максимум stale 15 минут, затем закрывать редактирование до успешной проверки. Периодическая синхронизация с jitter, rate-limit headers/backoff. EventSub не гарантирует replay после обрыва; на один пользовательский токен есть лимиты WebSocket/подписок, поэтому считать подписки и не плодить сокеты. Старая TTS очередь теряет pending redemption при падении — требуется мониторинг/ручное урегулирование.
- **Ресурсы:** несколько каналов увеличат число WebSocket, API-вызовов, SQLite-записей и TTS Python процессов. Ограничить общую конкуренцию TTS/память, следить за диском (`uploads`, WAV, backup), CPU и размером БД. Docker-образ сейчас не содержит Python/модель TTS.
- **TLS/proxy:** в `nginx.conf.example` только HTTP; production OAuth требует стабильный HTTPS origin, точные redirect URIs, WebSocket Upgrade и `Secure` cookie. `trust proxy` намеренно false; не доверять `X-Forwarded-For` без отдельного проекта и тестов. При одном proxy IP лимиты входа общие. Не публиковать локальный obs-websocket.
- **Совместимость OBS:** новые размеры в приложении не меняют конфигурацию Browser Source; стример вручную обновляет Width/Height. Старые URL/токены и медиа файлы должны работать без ротации. Перед выкладкой — staging-копия, тест на реальном OBS и заранее проверенный restore; после выкладки — проверка двух каналов и логов без секретов.

## План проверки

Автоматические тесты — в изолированной временной SQLite с проверкой фактического пути через `PRAGMA database_list`, mock HTTP Twitch и минимум двумя каналами. Использовать имеющийся HTTP+Socket.IO стенд `tests/securityIntegration.test.ts`; не запускать тесты на рабочей БД.

| Группа | Что проверить |
| --- | --- |
| OAuth | state/TTL/одноразовость/replay/login CSRF, точный redirect, отказ Twitch, обмен кода сервером, новый стример и модератор, повторный вход и обновление профиля, scopes, refresh 401/параллельность/revoke, logout и session expiry, отсутствие токенов в URL ответа/логах. |
| Миграция | Backfill на копии старой БД дважды, сохранение ID/counts/путей медиа/overlay URL/TTS reward, безопасная привязка и конфликт Twitch ID, восстановление из backup, legacy-вход только в старый канал. |
| Роли | Полная pagination `Get Moderators` и `Get Moderated Channels`, свежесть TTL, локальный запрет после sync, снятие/возврат запрета, удаление модератора на Twitch, 429/401/5xx/частичный sync, закрытие доступа после stale window, мгновенный Socket.IO revoke. |
| Изоляция | Создание двух каналов, чтение/мутация чужого channelId/mediaId/elementId/custom emote/OBS token/TTS, `/uploads` GET/HEAD/Range с cookie и токенами разных каналов, room events, reconnect, присутствие, quota, одновременные модераторы, поведение logout/ротации. |

После каждого изменяющего этапа: focused tests, затем `npm run typecheck`, `npm run lint`, `npm test`, `npm run build`, `git diff --check`; перед коммитом diff на секреты, runtime-файлы и побочные изменения.
