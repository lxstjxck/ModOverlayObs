# Проверка безопасности — 20 сентября 2026

## Разделение локальной и Twitch-авторизации — 15 октября 2026

Доступ к редактору, сценам, OBS URL, медиа, Socket.IO и настройкам каналов предоставляется только действующей Twitch-сессии с проверенной ролью на конкретном канале. Глобальная роль `OWNER` в локальной записи больше не определяет владельца Twitch-канала. Прежние `LEGACY`-сессии остаются в БД до истечения срока, но не авторизуют редактор или защищённые медиа. Локальная учётная запись не удаляется; административная панель и административный вход пока не активны.

Парольный маршрут `/legacy-login` используется только для переноса первого ещё не привязанного канала: после входа сессия позволяет начать привязку к Twitch, но не управлять сценой. Когда канал привязан, `/api/auth/login` закрыт. Обычный Twitch OAuth может заменить старую локальную cookie; привязка сохраняет существующие каналы, сцены, медиа, настройки и OBS-токен. Ранее скопированный OBS URL остаётся отдельным действующим токеном; его отзыв требует отдельной ротации владельцем. Схема SQLite не меняется. Старые TTS-маршруты не получают доступа от локальной сессии; управление Twitch TTS остаётся у проверенного владельца канала через маршруты с ID канала.

## Автоматическая перепроверка Socket.IO-доступа — 15 октября 2026

Открытые редакторские Socket.IO-соединения проверяются сервером каждые 5 секунд без действий клиента. Для каждого канала сервер использует один список Twitch-модераторов: успешный снимок действует 10 секунд, по истечении срока выполняется одна синхронизация на канал с защитой от параллельных одинаковых запросов и пределом ожидания 10 секунд. Сессия, OAuth-доступ, роль и локальный запрет проверяются для каждого сокета. При подтверждённом отзыве сокет сначала выходит из комнаты канала и отключается; при недоступности Twitch и устаревшем снимке доступ модератора закрывается. Владелец проверяется отдельно и не обязан находиться в списке модераторов. Сокеты OBS по overlay-токену в этот опрос не входят. Локальный ban, logout и отзыв OAuth сохраняют немедленное отключение через существующие события. Опрос и его таймер работают в одном процессе и завершаются при закрытии HTTP-сервера.

## Единый Twitch-вход — 13 октября 2026

OAuth-вход запрашивает оба scope: `moderation:read` и `user:read:moderated_channels`. Ответ callback проверяет оба scope и Twitch User ID; отказ в разрешениях не создаёт сессию. Новая сессия имеет режим `unified`; старые сессии режимов `streamer` и `moderator` больше не авторизуют API. Записи OAuth старых режимов не удаляются. При новом входе создаётся зашифрованная запись `unified` в существующей таблице. Миграция схемы не требуется.

Привязка legacy-канала требует действующую локальную OWNER-сессию и одноразовое OAuth-состояние, связанное именно с ней. После успешной привязки эта сессия уничтожается и создаётся единая Twitch-сессия; данные канала сохраняются.

На каждом канале сервер отдельно определяет owner по `ownerUserId` и `twitchBroadcasterId` или moderator по актуальному списку Twitch и локальному запрету. Проверка токена подтверждает client ID, User ID и оба scope; положительный результат и список модераторов действуют не более 10 секунд. Ошибка Twitch API не продлевает снимок. Отозванный refresh token или scope закрывает доступ и отключает сокеты пользователя. Параметры URL, заголовки и Socket.IO query выбирают лишь канал для проверки и не задают роль. TTS продолжает запрашивать свои отдельные scope только владельцу канала.

Ниже сохранено описание прежних этапов реализации для истории; параметры кэша и выбор режима входа в них заменены правилами этого раздела.

## Смена ссылки OBS Browser Source — 15 октября 2026

С версии 0.1.10 смена OBS URL доступна только действующей Twitch-сессии подтверждённого владельца выбранного канала. Маршрут требует CSRF, ограничивает частоту до пяти операций в час на пользователя и отклоняет одновременную смену ссылки для одного канала. Новый токен записывается атомарно, прежний перестаёт проходить HTTP/Socket.IO-проверки, подключённые по нему OBS-клиенты отключаются. Живые экземпляры и настройки холста сохраняются; новая ссылка должна быть вручную установлена в OBS. Ответ с новой ссылкой использует `Cache-Control: private, no-store`; токены не пишутся в аудит.

## Удалённая перезагрузка OBS Browser Source — 13 октября 2026

Команда доступна только действующей Twitch-сессии режима «Стример», чьему `User.id` принадлежит выбранный канал; сервер повторно проверяет доступ при каждом HTTP-запросе. OBS-сокеты выбираются только из комнаты этого канала. Для каждого подключения создаётся отдельный одноразовый идентификатор попытки. Ответ на команду учитывается лишь как получение, а успешным результатом считается новое OBS-подключение, которое после `overlay:state` сообщает этот идентификатор. Операция ограничена 15 секундами; повторные команды блокируются на время операции и 10 секунд после её завершения. Статус не содержит OBS URL или overlay-токен. Состояние операции находится в памяти одного процесса: перезапуск сервера прерывает наблюдение за уже начатой операцией. При полном зависании Browser Source требуется ручная перезагрузка в OBS. Интеграционные тесты проверяют авторизацию, несколько клиентов, переподключение и изоляцию каналов; таймаут проверяется отдельно.

## Twitch OAuth, этап 1 — 12 октября 2026

Новый вход использует серверный Authorization Code Flow с одноразовым состоянием в SQLite. Случайный `state` привязан к отдельному HttpOnly cookie, точному callback URL, режиму и сроку 10 минут. Callback атомарно удаляет состояние до обмена кода, проверяет client ID, постоянный Twitch User ID и выданный scope. Access/refresh tokens шифруются AES-256-GCM отдельным стабильным ключом из `OAUTH_TOKEN_ENCRYPTION_KEY` и не выдаются клиенту. Сессия использует существующий HttpOnly SameSite=Lax cookie; Secure включён в production. Ошибки редиректят на страницу входа без кода, токена и state.

Старый парольный вход и OBS bearer URL сохраняются. Выбор «Стример/Модератор» задаёт набор scopes; права на конкретный канал сервер проверяет отдельно для каждого HTTP-запроса и действия Socket.IO.

## Twitch OAuth, доступ к каналам — 12 октября 2026

Самостоятельное подключение канала доступно только с Twitch-сессией режима «Стример». Сервер повторно проверяет access token через Twitch `/validate`, соответствие client ID, Twitch User ID и scope; уникальные индексы `ownerUserId` и `twitchBroadcasterId` защищают от дубликатов при параллельных запросах. Создание задаёт отдельный случайный 256-битный overlay-токен, начальный холст 1920×1080 и пустые настройки. Повторный запрос возвращает существующий канал. Legacy-канал, его владелец, URL, медиа и TTS-настройки не меняются. Новая миграция добавляет только уникальный индекс `twitchBroadcasterId`; её применение к старой базе требует предварительной проверки отсутствия дубликатов и backup.

На новой установке с полной Twitch OAuth-конфигурацией `INITIAL_ADMIN_PASSWORD` может быть пустым: legacy OWNER-аккаунт не создаётся. Если пароль указан, прежняя проверка минимальной длины и запрета шаблонного значения остаётся обязательной.

Редактор и загрузки требуют явного ID Twitch-канала в HTTP/Socket.IO. Сервер проверяет доступ для каждого запроса и realtime-изменения; OBS и модераторы находятся в отдельных комнатах на канал. Только владелец канала получает OBS URL или сырой overlay-токен, включая legacy-вход. Отзыв локального запрета отключает сокеты модератора только в соответствующем канале. GET, HEAD и Range для загруженных файлов сверяют владельца записи Media с каналом сессии или OBS-токена. Модераторский список при недоступности Twitch может использовать только успешный снимок возрастом до 15 минут; права всё равно проверяются на сервере и истекают при устаревании снимка.

TTS привязан к явному `channelId`: Twitch-владелец получает отдельное согласие, настройки и EventSub-подключение своего канала. Legacy-канал сохраняет прежнюю запись настроек и OBS URL. Команды принимаются только при совпадении broadcaster ID в событии с ID канала; очередь, cooldown, активный WAV и OBS-комната изолированы. Клиент не может выбрать другой канал для TTS по прямому URL.

Настройки холста меняет только подтверждённый Twitch-владелец с привязанным `ownerUserId` через явный `channelId`. Сервер проверяет канал, размеры, режим и ожидаемую ревизию в существующем `Streamer.settingsJson`. Размер и геометрия preview/live меняются одной SQLite-транзакцией; повторная отправка старой ревизии получает 409. Realtime-изменения preview проверяют ревизию под общим для канала замком, чтобы задержанные действия старого редактора не применились после смены размера. Замок рассчитан на один серверный процесс, как и существующий механизм отзыва Socket.IO. Browser Source не предоставляет приложению свой фактический Width/Height: предупреждение в панели сравнивает размер холста с вручную введёнными размерами источника.

Привязка существующего канала запускается через `/api/auth/twitch/start/bind` только с действующей legacy OWNER-сессией. OAuth state привязан к хешу именно этой сессии; callback проверяет её повторно, затем Twitch ID, scope и отсутствие уже привязанного владельца. Привязка добавляет `ownerUserId` и Twitch ID к существующей записи `Streamer` без смены её ID, overlay-токена, медиа, TTS или настроек. Повторная привязка запрещена. OAuth-токены остаются зашифрованными в отдельной записи пользователя.

Сервер получает полные списки `Get Moderators` и `Get Moderated Channels` с проверкой всех страниц. Снимок модераторов заменяется только после полного успешного ответа. Положительная проверка действует 5 минут; при временной ошибке Twitch последний успешный снимок допускается максимум 15 минут, затем доступ закрывается. Обновление access token выполняется по истечении срока или после HTTP 401 с одним параллельным refresh на подключение; недействительный refresh или потеря scope отзывают подключение. Локальный запрет владельца проверяется раньше снимка и немедленно уведомляет активные сокеты. Обнаруженное удаление модератора при обновлении списка также отзывает сокеты.

Единая проверка `canAccessChannel(session, channelId)` применяется к HTTP API, Socket.IO и `/uploads`. Legacy-сессии ограничены первым каналом; Twitch-сессии получают доступ только к явно выбранному разрешённому каналу. OBS overlay-токен привязан к конкретному каналу, включая GET, HEAD и Range.

Миграция `20261012_channel_access_stage2` только добавляет столбцы и таблицы. Перед применением на production нужны остановка сервиса, проверенный backup SQLite вместе с WAL и uploads, репетиция на копии и проверка старого OBS URL. Приложение не запускает её автоматически в этой задаче.

## Ссылки eblo.id

При добавлении ссылки на публикацию сервер обращается только к точному HTTPS-хосту `eblo.id`, без перехода по редиректам, с таймаутом и ограничением размера HTML. Из страницы принимается только прямой медиафайл из `/uploads/<код публикации>/` того же хоста. Тип файла определяется по расширению и затем проверяются соответствующие права загрузки. Исходная страница и её HTML не сохраняются; в SQLite сохраняется прямой URL файла. Внешний сайт может изменить разметку или удалить файл, тогда добавление либо воспроизведение перестанет работать.

## Twitch TTS

- Подключение Twitch выполняет владелец через OAuth. Для новых каналов одноразовый `state` хранится в SQLite и привязан к отдельному HttpOnly cookie, точному redirect URI, Twitch-сессии стримера и ID принадлежащего ему канала; callback атомарно расходует state, проверяет client ID, Twitch User ID и только scopes `user:read:chat` и `channel:manage:redemptions`. Access/refresh tokens шифруются AES-256-GCM перед сохранением в `Settings`: новые записи используют стабильный `OAUTH_TOKEN_ENCRYPTION_KEY` и префикс версии, legacy-записи сохраняют прежний ключ из `SESSION_SECRET`. Смена соответствующего ключа требует повторного подключения Twitch. Токены не выдаются модераторам и не включаются в JSON или диагностические логи. Legacy OAuth-адрес и формат настроек совместимы.
- Сервер проверяет `moderator` badge в EventSub для бесплатной команды `!tts`. Для зрителей принимает только redemption созданной приложением награды нужного канала. Клиент не может отправить текст на озвучку через Socket.IO. Текст ограничен 200 символами; очередь — 10 ожидающими фразами на канал и 100 суммарно, частота — одна фраза в 30 секунд на пользователя каждого канала.
- WAV отдаётся по случайному идентификатору только пока фраза воспроизводится в OBS. Идентификатор не является overlay-токеном. Подтверждение воспроизведения принимается только от того OBS-сокета, которому сервер отправил фразу. При ошибке генерации, отключении OBS или ошибке воспроизведения награда отменяется и баллы возвращаются, если Twitch API доступен.
- Twitch EventSub использует отдельный WebSocket на включённый канал, восстановление после перезапуска и проверку токена каждые 5 минут. Отзыв подписки, ошибка обновления токена 400/401 или отказ Twitch API 401/403 останавливают только затронутый канал и сохраняют видимую владельцу ошибку. Временная недоступность Twitch запускает повторное соединение с задержкой от 5 до 60 секунд и небольшим случайным разбросом. После аварийного перезапуска уже принятые, но ещё не обработанные награды могут остаться в Twitch со статусом UNFULFILLED и потребуют ручной проверки. Ошибка Twitch API при завершении награды тоже может оставить её в этом статусе.
- Общий диспетчер запускает не более одного Python-процесса одновременно и обходит очереди каналов по кругу; воспроизведение готовых фраз в разных OBS идёт независимо. На генерацию даётся 60 секунд, на воспроизведение — 90 секунд; отключение канала прерывает его текущую генерацию. Временные `tts-*.wav` удаляются после обработки; файлы старше 10 минут удаляются при запуске и в ходе работы. Очистка ограничена точным форматом имён WAV в `uploads/.tmp`, остальные загрузки не затрагиваются. Одно длительное поколение может задержать другой канал максимум до тайм-аута; на VPS рекомендуется ограничить память сервиса. До запуска на реальном канале нужен ручной тест звука в OBS и проверки возврата баллов при отключённом OBS.

## Channel Emotes v0.1.2

Twitch credentials хранятся только в серверном окружении. Twitch/7TV metadata запрашивается с фиксированных API hosts; произвольный Custom URL сервер не скачивает, поэтому серверный SSRF через Custom невозможен. Прямые Custom URL ограничены HTTPS и расширениями PNG/JPEG/GIF/WebP, но фактический MIME/содержимое не проверяются сервером. Браузер запрашивает URL напрямую. Существующий `img-src https:` допускает произвольные HTTPS hosts ради внешних изображений; более узкий статический CSP несовместим с произвольными Custom URL. Для emotes используются те же права создания preview, что и для других элементов. Удаление Custom metadata не удаляет preview/live элементы и не касается uploads.

Проверены сервер, клиент, схема SQLite, правила исключения файлов и зависимости.
Это проверка кода и локальные тесты, а не внешний пентест.

## Исправленные проблемы

1. **Отзыв Socket.IO-доступа.** Выход отключает все соединения именно этой сессии,
   ротация overlay-токена — соединения со старым токеном. Истечение сессии
   отключает даже неактивный сокет. Перед изменением состояния сервер заново
   проверяет сессию и актуальные права. Подписка на отзыв начинается до проверки
   подключения, чтобы не пропустить отзыв во время авторизации.
2. **Подмена IP.** `X-Forwarded-For` не используется для ограничения входа;
   учитывается адрес транспортного соединения. Лимит на имя аккаунта независим
   от IP. `trust proxy` отключён. При работе через прокси IP-лимит общий для
   клиентов этого прокси.
3. **Права на эфир.** Поскольку полотно непосредственно транслируется в OBS,
   добавление, перемещение, изменение, дублирование и удаление элементов требуют
   одновременно `canEditPreview` и `canPushLive`. Это проверяется сервером;
   браузер также блокирует локальные изменения без этих прав.
4. **Доступ к файлам.** `/uploads` требует действующую сессию или overlay-токен
   соответствующего стримера. Файл должен быть зарегистрирован в базе.
   Проверяются также HEAD и Range-запросы; перемотка видео сохраняется.
   Ответы используют `Cache-Control: private, no-store`. OBS добавляет токен
   только к внутренним путям файлов, никогда к внешним ссылкам.
5. **Квота и очистка.** Проверка занятого места, создание записи медиа и аудит
   выполняются в одной Serializable-транзакции. Очередь записи предотвращает
   конфликт параллельных загрузок внутри процесса. При ошибке проверки, отказе
   прав, превышении квоты или откате транзакции файлы удаляются в `finally`.

Отзыв сокетов рассчитан на один процесс сервера. Для нескольких экземпляров
потребуется общий канал отзыва доступа. Уже скачанные материалы отозвать нельзя.
Multer 2.4.0 удаляет временный файл при прерывании запроса. После аварийного
завершения процесса уборка при следующем запуске и каждый час ищет только файлы
с 32 шестнадцатеричными символами в `uploads/.tmp`. Файлы моложе 24 часов,
активные загрузки текущего процесса, символические ссылки и каталоги пропускаются;
за проход удаляется не более 100 файлов. Порог в 24 часа значительно больше
обычной длительности одной загрузки; активный файл остаётся
защищённым и при более долгой загрузке. Ошибка отдельного файла не останавливает
сервер. TTS WAV, зарегистрированные медиа в основном `uploads/` и данные SQLite
не затрагиваются. После аварии файл сохраняется до следующей уборки и достижения
порога возраста; при отказе файловой системы уборка может не сработать.
Проверка сиротских файлов уже в основном `uploads/` по таблице `Media` остаётся
отдельным улучшением.

## Проверки

Перед production Twitch TTS выключен по умолчанию и при `TTS_ENABLED=false`. Сервер не запускает EventSub, обработку озвучивания или генератор речи; все маршруты мутации TTS и наград отвечают 503. Данные TTS и OAuth остаются в SQLite без изменений. Уже созданная награда Twitch остаётся доступной зрителям, пока владелец не отключит её вручную в Creator Dashboard; порядок указан в `docs/PRODUCTION_DEPLOYMENT.md`.

Интеграционные тесты используют настоящий HTTP, Socket.IO и отдельную временную
SQLite-базу. Перед очисткой тестовых данных проверяется фактический путь базы
через `PRAGMA database_list`; несовпадение прерывает тесты.

Проверяются выход нескольких вкладок, независимость сессий, смена токена,
истечение сессии, актуальность прав, закрытый доступ к файлам, HEAD/Range,
параллельная квота, откат при ошибке аудита и очистка неуспешных загрузок.
Есть отдельная проверка отсутствия утечки overlay-токена во внешние URL.

При первоначальном запуске новых тестов произошла ошибка изоляции и рабочая база
была перезаписана. Пользователь подтвердил, что восстанавливать данные не нужно.
Тестовые записи удалены, аккаунт владельца заново создан из `.env`, overlay-токен
обновлён. После исправления изоляции тесты выполняются на временной базе.

## Что ещё улучшить

- При первом запуске владелец создаётся только с заданным `INITIAL_ADMIN_PASSWORD` длиной
  не менее 12 символов; прежний шаблонный пароль отклоняется. После создания
  аккаунта переменная не меняет его пароль и не обязательна для запуска.
- Ограничить схему `props`, количество элементов полотна и объём состояния.
  Сейчас авторизованный редактор может создавать избыточную нагрузку.
- Добавить смену пароля и управление сессиями. `INITIAL_ADMIN_PASSWORD`
  применяется только при создании владельца; его изменение не обновляет
  существующий пароль.
- Проверять полномочия на переименование медиа: сейчас достаточно авторизации.
- Добавить резервное копирование с проверкой восстановления и сверку медиа
  в основном `uploads/` с базой после аварий. Сигнатура файла не заменяет полную проверку декодером.
- Показывать ошибки загрузки внешних медиа. Они загружаются браузером напрямую;
  внешнему источнику виден IP клиента. HTTP-медиа могут блокироваться на HTTPS-странице.
- Добавить error boundary, отмену действий и более явный статус сохранения.

`.gitignore` и `.dockerignore` исключают локальные данные и секреты, но не удаляют
их из уже созданных коммитов и образов. Ранее выполненный `npm audit` сообщил
0 известных уязвимостей; это не доказывает отсутствие ошибок приложения.
